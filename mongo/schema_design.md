# Проектирование документной модели MongoDB

Проект: **RideSharing REST API**  
Вариант: **7 — Сервис поиска попутчиков**

## 1. Цель проектирования

Цель данной работы — спроектировать документную модель MongoDB для сервиса поиска попутчиков.

Система содержит следующие основные сущности:

- Пользователь
- Маршрут
- Поездка

Основные операции варианта:

- создание нового пользователя;
- поиск пользователя по login;
- поиск пользователя по маске имени и фамилии;
- создание маршрута;
- получение маршрутов пользователя;
- создание поездки;
- подключение пользователей к поездке;
- получение информации о поездке.

## 2. Коллекции MongoDB

Для системы используются следующие коллекции:

```text
users
routes
trips

3. Коллекция users

Коллекция users хранит данные пользователей.

Пример документа:

{
  _id: ObjectId("..."),
  login: "driver1",
  password_hash: "hash_123456",
  first_name: "Ivan",
  last_name: "Petrov",
  role: "DRIVER",
  rating: 4.8,
  phone: "+79990000001",
  created_at: ISODate("2026-05-20T10:00:00Z")
}
Поля

Поле	Тип	Описание
_id	ObjectId	Уникальный идентификатор пользователя
login	String	Уникальный login пользователя
password_hash	String	Хеш пароля
first_name	String	Имя
last_name	String	Фамилия
role	String	Роль пользователя: DRIVER или PASSENGER
rating	Number	Рейтинг пользователя
phone	String	Телефон
created_at	Date	Дата создания пользователя


Почему отдельная коллекция?

Пользователи используются в разных частях системы:

как владельцы маршрутов;
как водители поездок;
как пассажиры поездок.

Поэтому хранить пользователей в отдельной коллекции удобнее и правильнее. Если встраивать пользователя внутрь каждого маршрута или поездки, данные будут дублироваться, и при изменении имени, рейтинга или телефона пользователя нужно будет обновлять много документов.

4. Коллекция routes

Коллекция routes хранит маршруты пользователей.

Пример документа:

{
  _id: ObjectId("..."),
  user_id: ObjectId("..."),
  from_city: "Moscow",
  to_city: "Tver",
  distance_km: 180,
  tags: ["intercity", "popular"],
  created_at: ISODate("2026-05-20T10:00:00Z")
}
Поля

Поле	Тип	Описание
_id	ObjectId	Уникальный идентификатор маршрута
user_id	ObjectId	Ссылка на пользователя, который создал маршрут
from_city	String	Город отправления
to_city	String	Город назначения
distance_km	Number	Расстояние в километрах
tags	Array	Дополнительные теги маршрута
created_at	Date	Дата создания маршрута


Почему user_id как reference?

Маршрут связан с пользователем, но пользователь является отдельной самостоятельной сущностью. Один пользователь может создать много маршрутов.

Связь:

users 1 → N routes

Используется reference:

user_id: ObjectId("...")

Это уменьшает дублирование данных и позволяет отдельно обновлять данные пользователя.

5. Коллекция trips

Коллекция trips хранит поездки.

Пример документа:

{
  _id: ObjectId("..."),
  driver_id: ObjectId("..."),
  route_id: ObjectId("..."),
  departure_time: ISODate("2026-05-25T10:00:00Z"),
  available_seats: 3,
  price: 1200,
  status: "ACTIVE",
  passengers: [
    {
      user_id: ObjectId("..."),
      joined_at: ISODate("2026-05-20T12:00:00Z")
    }
  ],
  created_at: ISODate("2026-05-20T10:00:00Z")
}

Поля

Поле	Тип	Описание
_id	ObjectId	Уникальный идентификатор поездки
driver_id	ObjectId	Ссылка на пользователя-водителя
route_id	ObjectId	Ссылка на маршрут
departure_time	Date	Время отправления
available_seats	Number	Количество свободных мест
price	Number	Цена
status	String	Статус поездки
passengers	Array of Objects	Встроенный список пассажиров
created_at	Date	Дата создания поездки

6. Embedded documents vs References

6.1 References

References используются для связей между основными сущностями:

routes.user_id → users._id
trips.driver_id → users._id
trips.route_id → routes._id

Причины выбора references:

пользователь и маршрут являются самостоятельными сущностями;
данные пользователя не нужно дублировать в каждом маршруте и поездке;
один пользователь может иметь много маршрутов и поездок;
один маршрут может использоваться в поездке;
такой подход ближе к реальной архитектуре приложения.
6.2 Embedded documents

Embedded documents используются для пассажиров внутри поездки:

passengers: [
  {
    user_id: ObjectId("..."),
    joined_at: ISODate("...")
  }
]

Причины выбора embedded documents:

пассажиры обычно нужны вместе с информацией о поездке;
список пассажиров является частью состояния поездки;
операция подключения пользователя к поездке удобно реализуется через $addToSet или $push;
для получения информации о поездке не нужно читать отдельную коллекцию связи;
количество пассажиров ограничено количеством мест в машине, поэтому массив не будет слишком большим.
7. Связи между коллекциями
users 1 → N routes
users 1 → N trips as driver
routes 1 → N trips
trips 1 → N embedded passengers
users N → N trips through embedded passengers
8. Индексы

Для частых запросов рекомендуется создать индексы:

db.users.createIndex({ login: 1 }, { unique: true })
db.users.createIndex({ first_name: 1, last_name: 1 })

db.routes.createIndex({ user_id: 1 })
db.routes.createIndex({ from_city: 1, to_city: 1 })

db.trips.createIndex({ driver_id: 1 })
db.trips.createIndex({ route_id: 1 })
db.trips.createIndex({ status: 1, departure_time: 1 })
db.trips.createIndex({ "passengers.user_id": 1 })
Назначение индексов
Индекс	Для чего нужен
users.login	Быстрый поиск пользователя по login
users.first_name + users.last_name	Поиск пользователя по маске имени и фамилии
routes.user_id	Получение маршрутов конкретного пользователя
routes.from_city + routes.to_city	Поиск маршрутов по направлению
trips.driver_id	Поиск поездок водителя
trips.route_id	Поиск поездок по маршруту
trips.status + trips.departure_time	Поиск активных поездок по времени
trips.passengers.user_id	Поиск поездок пользователя как пассажира


9. Итоговая модель

Итоговая модель использует гибридный подход:

основные сущности хранятся в отдельных коллекциях;
связи между крупными сущностями реализованы через references;
пассажиры встроены внутрь документа поездки как embedded array.

Такой подход хорошо подходит для сервиса поиска попутчиков, потому что позволяет эффективно получать информацию о поездке вместе со списком пассажиров и при этом не дублировать основные данные пользователей и маршрутов.
