# Домашнее задание 05: Кеширование и Rate Limiting

Проект: **RideSharing REST API**  
Вариант: **7 — Сервис поиска попутчиков**

## 1. Цель работы

Цель работы — проанализировать производительность REST API сервиса поиска попутчиков, определить частые операции, спроектировать стратегию кеширования и rate limiting, а также описать влияние этих механизмов на производительность системы.

Система содержит сущности:

- Пользователь
- Маршрут
- Поездка

Основные операции:

- создание пользователя;
- поиск пользователя по login;
- поиск пользователя по маске имени и фамилии;
- создание маршрута;
- получение маршрутов пользователя;
- создание поездки;
- подключение пользователя к поездке;
- получение информации о поездке.

## 2. Анализ производительности

### 2.1 Hot paths

Hot paths — это операции, которые выполняются чаще всего.

| Endpoint | Причина высокой нагрузки |
|---|---|
| `GET /api/v1/users/by-login/{login}` | Частый поиск пользователя по login |
| `GET /api/v1/users/search` | Поиск пользователей по имени и фамилии |
| `GET /api/v1/users/{user_id}/routes` | Просмотр маршрутов пользователя |
| `GET /api/v1/trips/{trip_id}` | Частый просмотр информации о поездке |
| `POST /api/v1/auth/login` | Частый endpoint, требующий защиты от brute force |
| `POST /api/v1/trips/{trip_id}/join` | Операция изменения состояния поездки |

### 2.2 Потенциально медленные операции

Медленными могут быть:

- обращения к PostgreSQL;
- обращения к MongoDB;
- JOIN-запросы для получения поездки с водителем, маршрутом и пассажирами;
- aggregation pipeline в MongoDB;
- поиск по маске имени и фамилии;
- частые попытки авторизации.

### 2.3 Требования к производительности

| Операция | Целевое время ответа |
|---|---|
| Получение пользователя по login | до 50 мс при cache hit |
| Получение поездки по id | до 100 мс при cache hit |
| Получение маршрутов пользователя | до 100 мс |
| Создание маршрута | до 200 мс |
| Создание поездки | до 200 мс |
| Подключение пользователя к поездке | до 200 мс |
| Login | до 150 мс |

## 3. Стратегия кеширования

### 3.1 Инструмент кеширования

Для кеширования выбран **Redis**.

Причины выбора:

- высокая скорость работы;
- поддержка TTL;
- удобное key-value хранилище;
- хорошо подходит для Cache-Aside;
- легко запускается через Docker Compose.

### 3.2 Что кешировать

| Данные | Endpoint | TTL | Причина |
|---|---|---|---|
| Пользователь по login | `GET /api/v1/users/by-login/{login}` | 5 минут | Данные часто читаются и редко меняются |
| Информация о поездке | `GET /api/v1/trips/{trip_id}` | 30 секунд | Частый read endpoint |
| Маршруты пользователя | `GET /api/v1/users/{user_id}/routes` | 2 минуты | Часто открывается в профиле пользователя |
| Поиск пользователей | `GET /api/v1/users/search` | 1 минута | Частый поиск по имени и фамилии |

### 3.3 Выбранная стратегия: Cache-Aside

Алгоритм Cache-Aside:

```text
1. API получает GET-запрос.
2. API проверяет Redis.
3. Если данные найдены — возвращает ответ из кеша.
4. Если данных нет — читает из основной базы данных.
5. API сохраняет результат в Redis с TTL.
6. API возвращает ответ клиенту.

Преимущества:

простая реализация;
API полностью контролирует кеш;
можно гибко настраивать TTL;
удобно инвалидировать кеш при изменении данных.
3.4 Redis keys

Примеры ключей:

user:login:driver1
user:routes:1
trip:1
users:search:first_name=Iv:last_name=Pet
3.5 Инвалидация кеша
Операция	Что инвалидировать
Создание пользователя	user:login:{login}
Обновление пользователя	user:login:{login} и результаты поиска
Создание маршрута	user:routes:{user_id}
Создание поездки	trip:{trip_id}
Подключение пассажира к поездке	trip:{trip_id}
Отмена поездки	trip:{trip_id}
3.6 Почему не Write-Back

Write-Back не выбран, потому что для поездок важна консистентность.
Например, при подключении пассажира нужно сразу обновить количество свободных мест в основной базе данных.

4. Rate Limiting
4.1 Зачем нужен rate limiting

Rate limiting нужен для:

защиты от brute force атак;
защиты login endpoint;
ограничения слишком частого поиска;
предотвращения спама при подключении к поездке;
защиты API от перегрузки.
4.2 Endpoints для rate limiting
Endpoint	Лимит	Причина
POST /api/v1/auth/login	5 запросов в минуту	Защита от brute force
GET /api/v1/users/search	60 запросов в минуту	Защита от массового поиска
POST /api/v1/trips/{trip_id}/join	10 запросов в минуту	Защита от спама
GET /api/v1/trips/{trip_id}	120 запросов в минуту	Защита read endpoint
4.3 Выбранный алгоритм

Для POST /api/v1/auth/login выбран алгоритм Fixed Window Counter.

Причины:

простой для реализации;
подходит для учебного проекта;
легко реализуется через Redis;
ключ хранится с TTL 60 секунд.

Пример ключа Redis:

rate:login:127.0.0.1

Алгоритм:

1. При каждом login-запросе увеличивается счетчик.
2. Если счетчик создан впервые — устанавливается TTL 60 секунд.
3. Если количество запросов больше лимита — возвращается 429 Too Many Requests.
4. Если лимит не превышен — запрос обрабатывается.
4.4 Ответ при превышении лимита

HTTP status:

429 Too Many Requests

Body:

{
  "error": "rate limit exceeded"
}

Headers:

X-RateLimit-Limit: 5
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 60
5. Реализация кеширования
5.1 Кешируемые endpoints

Минимум 2 endpoints:

GET /api/v1/users/by-login/{login}
GET /api/v1/trips/{trip_id}
5.2 Cache hit
Client → API → Redis → Response

Преимущества:

нет обращения к PostgreSQL/MongoDB;
меньше нагрузка на БД;
быстрее ответ.
5.3 Cache miss
Client → API → Redis miss → Database → Redis set with TTL → Response
5.4 Инвалидация при изменении поездки

При запросе:

POST /api/v1/trips/{trip_id}/join

нужно удалить ключ:

trip:{trip_id}

Потому что меняется:

количество свободных мест;
список пассажиров.
6. Анализ влияния на производительность
6.1 Как кеширование улучшает систему

Кеширование уменьшает:

количество запросов к базе данных;
среднее время ответа;
нагрузку на PostgreSQL и MongoDB;
задержку при повторных одинаковых запросах.
6.2 Как rate limiting улучшает систему

Rate limiting защищает от:

brute force;
перегрузки API;
слишком частого поиска;
спама на endpoint подключения к поездке.
7. Метрики мониторинга
Метрика	Описание
Cache hit rate	Доля запросов, обработанных из кеша
Cache miss rate	Доля запросов, ушедших в БД
Average response time	Среднее время ответа
p95 latency	95-й процентиль времени ответа
p99 latency	99-й процентиль времени ответа
Requests per second	Запросы в секунду
DB queries per second	Нагрузка на базу данных
Redis memory usage	Использование памяти Redis
Rate limited requests	Количество ответов 429
Error rate	Доля ошибок

Формула cache hit rate:

cache_hit_rate = cache_hits / (cache_hits + cache_misses) * 100%

Пример:

cache_hits = 800
cache_misses = 200

cache_hit_rate = 800 / (800 + 200) * 100% = 80%
8. Redis в Docker Compose

Redis запускается как отдельный сервис:

redis:
  image: redis:7
  container_name: ridesharing-redis
  ports:
    - "6379:6379"

Проверка Redis:

docker exec -it ridesharing-redis redis-cli ping

Ожидаемый ответ:

PONG

Rate limiting рекомендуется применять для:

В качестве кеша выбран Redis. Стратегия кеширования — Cache-Aside.

Такой подход уменьшает нагрузку на базу данных, ускоряет ответы API и защищает сервис от чрезмерного количества запросов.
